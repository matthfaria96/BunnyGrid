## Débitos técnicos conhecidos

- O AI Assistant não foi testado contra a API real nesta máquina (sem chave); o protocolo está coberto por testes unitários.
- BI e Create BI Workspace aparecem na interface, mas ainda mostram "em breve". Model já funciona (diagrama ER, layout salvo, PNG/PDF e Generate SQL); falta sincronizar modelo → banco e editar o modelo (só leitura, por enquanto), e as linhas que pulam uma camada podem cruzar cartões no meio. User (PostgreSQL/MySQL), Others, Export Wizard, Dump SQL e as ações de tabela (excluir, esvaziar, truncar, renomear, duplicar) já funcionam.

- Edições vão como parâmetros tipados escolhidos pelo tipo da coluna (inteiro, double, booleano, bytes, data/hora, NULL). Tipos que o app não modela (numeric, arrays, enums, geometria, intervalos) seguem como texto sem tipo declarado e o banco converte, como faria com um literal. Os três motores têm teste de integração do binding.
- No PostgreSQL, uma linha cuja chave primária é um `timestamp` com frações de segundo não pode ser editada: o valor chega ao grid sem as frações e o WHERE não acha a linha.
- O realce de sintaxe refaz o documento inteiro a cada tecla; trocar por tree-sitter (CodeEditSourceEditor) quando os scripts ficarem grandes.
- O editor SQL lê no máximo o limite de registros por resultado, mas Load More e Fetch All executam a consulta de novo (não há cursor aberto no servidor). No MySQL as linhas além do limite ainda trafegam e são descartadas (o MySQLNIO não tem backpressure); no PostgreSQL o PostgresNIO descarta o restante do stream.
- O Stop no PostgreSQL e no MySQL abre uma conexão curta para cancelar (o PostgresNIO não expõe o CancelRequest do protocolo); se o comando terminar antes e uma nova execução começar nesse intervalo, é ela que recebe o cancelamento.
- Os testes de integração do MySQL/MariaDB rodam contra o MySQL 26.7 do Homebrew (`scripts/test-servers/mysql.sh`, com SSL, certificado de cliente, socket e túnel SSH) e o MariaDB 11.8 no Docker; no MariaDB só não rodaram SSL com CA própria, certificado de cliente e socket. De vez em quando (algumas conexões em algumas centenas, num servidor local) o handshake do MySQLNIO trava sem responder ao servidor, que derruba a conexão depois do `connect_timeout` ("Got timeout reading communication packets"); o driver desiste do handshake depois de 6 s e tenta mais uma vez. A causa no MySQLNIO não foi encontrada.
- MySQL: um resultado sem linhas pega os nomes das colunas com um COM_STMT_PREPARE à parte (o MySQLNIO só entrega as definições junto com as linhas), ou seja, uma ida a mais ao servidor. Comandos que o protocolo de prepared statements recusa (`LOCK TABLES`, `CREATE PROCEDURE/TRIGGER`, …) caem no protocolo de texto, que não informa linhas afetadas.
- MySQL por socket: o servidor trata o socket como seguro e espera a senha em texto na autenticação completa do `caching_sha2_password`, mas o MySQLNIO só a manda assim sobre TLS (fora dele pede a chave RSA, e o servidor lê o pedido como senha errada). Por isso a conexão por socket usa TLS sem verificação quando o servidor oferece; um servidor sem SSL só aceita por socket usuários já no cache ou com `mysql_native_password`.
- Designer do MySQL/MariaDB: o `MODIFY COLUMN` repete AUTO_INCREMENT, ON UPDATE, INVISIBLE e o comentário da coluna, mas não charset/collation próprios da coluna nem a expressão de colunas geradas (mudar uma coluna gerada a transforma em coluna comum). O MariaDB informa RESTRICT nas chaves estrangeiras sem regra explícita.
- Exportação e importação carregam a tabela ou o arquivo inteiros na memória; o .xlsx é gravado sem compressão (zip STORE), então fica maior que o do Excel.
- Dump SQL do PostgreSQL recria as sequências de colunas `serial`, mas não colunas `GENERATED … AS IDENTITY`, tipos, extensões nem funções.
- Trocar a chave primária pelo designer só funciona no SQLite (reconstrução); no PostgreSQL e no MySQL ainda é recusado.
- A reconstrução de tabela do SQLite recusa CHECK, COLLATE, colunas geradas, WITHOUT ROWID, STRICT, ON CONFLICT e chaves DEFERRABLE (o designer não modela essas definições), e o contador de AUTOINCREMENT recomeça do maior id copiado. Os nomes de chaves estrangeiras do SQLite não aparecem (o `PRAGMA foreign_key_list` não os informa).
- Renomear um campo usado numa chave estrangeira não atualiza a linha da aba Foreign Keys (o banco renomeia a referência; no SQLite a reconstrução também).
- Túnel SSH: o Citadel assina chaves RSA com SHA-1 (`ssh-rsa`), que o OpenSSH 8.8+ recusa por padrão; o app mostra o motivo e sugere ed25519/ECDSA. Chaves ECDSA em formato OpenSSH só sem passphrase; chaves PEM criptografadas não são lidas. Login por senha não foi testado contra um servidor real (o sshd de teste roda sem root, só com chave). Sem keyboard-interactive, jump host nem agente SSH.
- A host key desconhecida é aceita e gravada sem perguntar (TOFU); o fingerprint aparece na aba SSH e no Test Connection, e uma chave diferente bloqueia a conexão até "Forget Host Key". Falta um diálogo de confirmação na primeira conexão.
- Quando a sessão SSH cai, as conexões abertas por ela falham; o próximo connect abre outro túnel, mas não há reconexão automática.
- Builds de desenvolvimento são assinados ad hoc: a cada rebuild o macOS pode pedir de novo acesso às senhas no Keychain. Com assinatura Developer ID isso não acontece.
- Transferência e sincronização: o Data Sync lê as duas tabelas inteiras e o Data Transfer pagina com OFFSET; falta cursor no servidor para tabelas grandes. Views só são comparadas entre motores iguais; CHECK, triggers, sequências, funções e comentários não entram no diff. Os testes do MySQL (`SyncIntegrationTests.swift`) ainda não rodaram contra um servidor real; os do PostgreSQL rodam.
- Automação: a janela Automation é uma janela própria, não uma aba do espaço de trabalho. Jobs têm passo de Data Transfer, mas ainda não de Data Sync / Structure Sync. O launch agent aponta para o executável no lugar em que estava quando o agendamento foi salvo: mover o app exige salvar o job de novo. Em builds assinados ad hoc o runner headless pode não conseguir ler as senhas do Keychain sem um aviso (que o launchd não mostra); conexões SQLite não precisam. Notificações só saem do app empacotado (`scripts/bundle.sh`).
- Backup e restauração carregam o script inteiro na memória. Um backup de schema do PostgreSQL usa nomes qualificados pelo schema, então restaura em outro banco com o mesmo schema (criado se não for `public`), não em outro schema. Funções, tipos e extensões não entram no backup (como no Dump SQL).
